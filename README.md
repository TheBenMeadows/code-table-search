# code-table-search

This repository holds an exact search for error-correcting codes that are invariant under a prescribed group of symmetries, and the BOINC application that runs the search on volunteer computers. The targets are the lower bounds in Andries Brouwer's tables of small codes over alphabets of 3, 4 and 5 symbols and over mixed binary/ternary alphabets, for lengths up to 16.

## Method

A code of length n over an alphabet of q symbols with minimum Hamming distance d is a set of words in which every two words differ in at least d coordinates. A_q(n,d) is the largest size of such a code. Let G be a group of coordinate permutations combined with symbol permutations at each coordinate; G acts on the words, and a code that G maps to itself is a union of G-orbits.

The program `osg` (src/osg.c) finds the largest G-invariant code:

1. It splits the q^n words into G-orbits.
2. It keeps an orbit as a vertex when the words of the orbit are pairwise at distance at least d. The weight of the vertex is the orbit size.
3. It joins two vertices by an edge when every word of one orbit is at distance at least d from every word of the other. Because the code is G-invariant, one representative of the first orbit is enough for this test.
4. It removes vertices whose weight plus the weight of their neighbours is below the target, and repeats until nothing changes.
5. It searches the remaining graph for a clique of maximum weight by branch and bound, with a colouring bound at each branch.

A clique of weight w is a G-invariant code of size w with minimum distance at least d. If the clique search finishes, the result is exact: no G-invariant code of size at least the target exists, or the largest one has been found.

For each table cell the search fixes a family group, such as AGL(1,12) on the coordinates with one symbol permutation applied at every coordinate. GAP (https://www.gap-system.org) and its transitive groups library list the subgroups of the family group up to conjugacy. One job is one subgroup class of one cell. This repository holds the group files of the 100 pilot units only.

## Layout

- `src/osg.c`: the search program (C, uses only the C library).
- `src/verifyx.py`: the exact checker for a returned code (Python, standard library).
- `Makefile`: builds `osg` and runs the two control searches (`make check`).
- `control/`: group and unit files for the two controls, the binary Hamming code and the ternary Golay code.
- `boinc/`: the BUDA application for BOINC Central: the job script `main_codetable_1.sh`, two Dockerfiles and `build_osg.sh`, which builds the static `osg` binaries.
- `pilot/`: the 100 pilot units. `pilot_units.tsv` lists them, `units/<unit>/unit.txt` and `units/<unit>/group.txt` are the job inputs, and `jobs.tsv` lists the 200 jobs (two replicas per unit).
- `tools/gen_batch.py`: turns a unit list into a BUDA batch file and a job list.
- `tools/assimilate.py`: reads returned results, checks every returned code again and records one result per unit.

## Build and run one search

Build `osg` with a C compiler (clang or gcc), then run the controls:

```
make
make check
```

`make check` runs two searches and checks each returned code. On an Apple M-series laptop the two searches take about 8 seconds together. The second control searches for the ternary Golay code, A3(11,5) = 729, under the group of order 22 generated by the cyclic shift of the 11 coordinates and the negation of every symbol:

```
./osg 3x11 5 control/A3-11-5/group.txt 729 60 130000 golay.txt
```

It prints:

```
G=22 orbits=8054 selfcompat=5641 alive=5641 nodes=984391 COMPLETE best=729
```

and writes the 729 code words to `golay.txt`. With target 730 the same search prints `COMPLETE best=-1`: no code invariant under this group has more than 729 words, which agrees with A3(11,5) = 729.

The arguments are:

```
osg ALPH D GROUPFILE TARGET TIME_LIMIT_S MAX_VERTICES OUTFILE
```

- `ALPH`: the alphabet sizes in coordinate order, as comma-separated blocks SIZExCOUNT: `3x11` is 11 ternary coordinates, `2x4,3x10` is 4 binary and then 10 ternary coordinates. At most 16 coordinates and at most 8 symbols per coordinate.
- `D`: the minimum distance.
- `GROUPFILE`: every element of the group, one element per line. An element is n integers for the coordinate permutation pi, followed by Q integers for each coordinate i giving the symbol map sigma_i, where Q is the largest alphabet size. The action is (g w)[pi[i]] = sigma_i[w[i]]. The file must list the whole group: `osg` does not close it under products, and a file that is not a group gives wrong orbits.
- `TARGET`: the smallest code size of interest. Cliques of smaller weight are not searched.
- `TIME_LIMIT_S`: the time limit in seconds for the clique search. Building the orbits and the graph is not counted.
- `MAX_VERTICES`: if more orbits than this are self-compatible, `osg` prints `TOO_MANY_VERTICES` and exits with status 3.
- `OUTFILE`: the file for the code words, written only when a code of size at least TARGET is found.

Fields of the output line:

- `G`: group order.
- `orbits`: number of orbits on words.
- `selfcompat`: orbits whose words are pairwise at distance at least d.
- `alive`: vertices left after pruning.
- `nodes`: search nodes.
- `COMPLETE` or `TIMEOUT`: whether the clique search finished.
- `best`: the largest clique weight found, or -1 when no clique reached the target.

## Result line and statuses

The BOINC job script and `tools/assimilate.py` use one tab-separated result line per job:

```
cell  fam  class  order  sig  target=T  bar=B  tl=CAP  secs=S  STATUS  osg-line
```

- `cell`: the table cell as A<q>-<n>-<d>: `A4-12-7` is A4(12,7).
- `fam`: the family group. `agl12_glob` is AGL(1,12) acting on 12 coordinates as x -> ax+b mod 12, with the same symbol permutation at every coordinate; `agl10_1_glob` is AGL(1,10) on 10 coordinates with one more coordinate fixed.
- `class`: the subgroup class within the family, `g<k>`.
- `order`: the order of the subgroup.
- `sig`: the sizes of the orbits of the subgroup on the coordinates, separated by dots.
- `target` and `bar`: the code size the search must reach, and the table's lower bound for the cell. In the pilot both are the table's lower bound.
- `tl` and `secs`: the time budget and the running time used, in seconds.

The status is one of:

- `WIN`: best > bar. A code larger than the table's lower bound was found.
- `BAR`: best = bar. A code that matches the table's lower bound was found.
- `LOW`: target <= best < bar.
- `NONE`: the clique search finished and found no invariant code of size at least the target.
- `TIMEOUT`: the time limit stopped the clique search before it finished.
- `TOO_MANY`: more self-compatible orbits than MAX_VERTICES.
- `KILLED`: the job script stopped `osg` at the hard limit.

`NONE` is the only negative status, and it is negative only for the subgroup of that job: no code invariant under that subgroup has at least `target` words. It says nothing about codes with other symmetries or with none. `TIMEOUT`, `TOO_MANY` and `KILLED` are never negatives. A `TIMEOUT` with best >= target is still a valid code of that size, and the job script reports it as `WIN`, `BAR` or `LOW`.

After the result line, a job that found a code writes a line `#CODE`, the header line of `osg`'s code file and the code words, one word per line.

## Verify a claimed code

A claimed code is checked exactly, without trusting `osg`:

```
python3 src/verifyx.py ALPH D CODEFILE
```

`verifyx.py` reads one word per line and ignores text after `#`. It checks four things:

- every word has n symbols;
- every symbol is in the alphabet of its coordinate;
- no word is repeated;
- every pair of words is at Hamming distance at least D.

It prints the number of words and the minimum distance, and exits with status 0 only if all checks pass. The size of the code is the number of words that it counted. `tools/assimilate.py` runs this check on every returned code and rejects a code whose word count differs from the reported `best`.

## The BOINC app

The app runs under BUDA (BOINC Universal Docker App) on BOINC Central. Each job gets two input files, `unit.txt` and `group.txt`, and returns `result.txt`.

`unit.txt` has one key=value pair per line: `cell`, `alph`, `d`, `target`, `bar`, `fam`, `class`, `order`, `sig`, `cap` and `maxv`. `cap` is the time budget in seconds of running time, and `maxv` is passed to `osg` as MAX_VERTICES. `group.txt` is the subgroup's element list in the GROUPFILE format above.

The job script `boinc/main_codetable_1.sh` runs `osg` with the remaining budget, writes the result line to `result.txt`, and reports progress in `fraction_done`. It counts running time in the file `elapsed_s`, so a job that is paused or restarted does not get a new budget. `osg` has no checkpoint: after a restart the search starts again from the beginning with the remaining budget, so a `NONE` always comes from one complete, uninterrupted search. If the whole run goes past cap + max(1800, cap/2) seconds, the script stops `osg` and the status is `KILLED`.

### Build the app files

The app binaries are static builds of `src/osg.c` for x86-64 and ARM64. Build them in a Debian container from the repository root:

```
sh boinc/build_osg.sh
```

This writes `boinc/osg_x86_64_1` and `boinc/osg_aarch64_1` and prints their SHA-256 sums.

### Run one job locally

Run the app on a Linux host with Docker, the same way BUDA runs it: the job directory is mounted at `/app` and the Dockerfile's command runs the job script.

```
mkdir -p /tmp/slot
cp control/A3-11-5/unit.txt control/A3-11-5/group.txt boinc/main_codetable_1.sh boinc/osg_x86_64_1 /tmp/slot/
mkdir -p /tmp/empty
docker build -t codetable-intel:1 -f boinc/Dockerfile_codetable_intel_cpu_1 /tmp/empty
docker run --rm --cpus 1 --network none -v /tmp/slot:/app codetable-intel:1
head -n 1 /tmp/slot/result.txt
```

The result line must end in `BAR` followed by the `osg` line with `COMPLETE best=729`. On an ARM64 host, use `Dockerfile_codetable_arm_cpu_1` and `osg_aarch64_1`.

The job script reads `/proc` to measure running time. On a host without `/proc` (macOS), the script still runs the search and writes the result line, but it reports `secs=0` and has no hard limit.

### Make a batch and read the results

`tools/gen_batch.py` turns a unit list into a BUDA batch file:

```
python3 tools/gen_batch.py pilot/pilot_units.tsv pilot/units 7200 2 out
```

This writes `out/batch.zip` (one directory per job with `unit.txt` and `group.txt`) and `out/jobs.tsv`. The command above rebuilds the pilot batch: 100 units, two replicas each, a budget of 7200 seconds per job. It refuses a group file whose number of elements differs from the group order in the unit list.

BUDA accepts any returned result, so a `NONE` cannot be trusted from one volunteer. Each unit runs as two jobs, usually on different hosts. After the jobs return, download the output zip from the batch page and run:

```
python3 tools/assimilate.py out/jobs.tsv OUTPUT.zip results.tsv codes
```

`assimilate.py` appends one result line per unit to `results.tsv` and skips units that it recorded before, so it can run again on later downloads. It rejects a result whose cell, family, class, target or bar differ from its job. It checks every returned code with `src/verifyx.py` and keeps the first verified `WIN`, then `BAR`, then `LOW`, in `codes/`. It records `NONE` only when at least two replicas returned `NONE` and no replica returned a verified code (`--min-agree` changes the number). When every replica is back and none of these holds, it records `TIMEOUT`, `TOO_MANY` or `KILLED`, which are never negatives.

## Pilot units

`pilot/pilot_units.tsv` lists 100 units on 50 cells of the ternary, quaternary and 5-ary tables. In every unit, `target` and `bar` equal a lower bound taken from Brouwer's table for that cell. `BAR` then means a code invariant under the subgroup matches that bound, and `WIN` means it beats that bound. For 49 of the 50 cells the bound is the one the table lists on 2026-11-25. For the two units on A5-9-6 the bound is 157 and the table now lists 166, so a code of 158 to 166 words on those units is `WIN` by the job's rule but no improvement on the table. `maxv` is 130000 for every unit.

## Results in Brouwer's tables

Earlier rounds of the same orbit method, which sampled subgroups at random instead of listing them all, found lower bounds that Brouwer's tables list as of 2026-11-25. The tables credit seven of them to Ben Meadows on the ternary, quaternary, 5-ary and mixed binary/ternary pages; an eighth, A4(11,7) >= 145, follows from A4(12,8) >= 145 by puncturing.

https://aeb.win.tue.nl/codes/ternary-1.html

https://aeb.win.tue.nl/codes/quaternary-1.html

https://aeb.win.tue.nl/codes/5ary-1.html

https://aeb.win.tue.nl/codes/23codes.html

Improved bounds found with this search are sent to Brouwer, and their codes will be archived on Zenodo.
